# 删除归档会话后「又回到对话列表」：归档只是遮罩，行要靠 `api-session/removed` 才真删

日期：2026-10-01
环境：DSH 桌面版 `0.2.0-rc.2`（`@deepseek-ai/*` 全部 0.2.0-rc.2）
插件：`@omdp/dsh-archived-sessions` 0.3.9 → 0.3.10

## 现象

用户报告：在「归档会话管理」里删除归档会话后，这些会话**又出现在对话列表中**，可以点选，
点进去报：

```
历史加载失败: session "session-7779ca7a-0a33-429c-acfa-3018374dbb76" not found (session/not-found)
```

重启 DSH 之后它们才真正消失。

## 排查结论（根因）

**这是客户端陈旧行，不是 Host 端删除失败。** 删除本身在服务端早就成功了（磁盘目录真的没了、
归档集合真的清了）。真正的机制是：

1. **归档在 DSH 里只是「可见性遮罩」，不是列表过滤条件。**
   - `dsh-session-query` 全库**零处** `archiv*` 匹配 ⇒ Host 的列表/查询层**从不**按归档过滤。
   - 归档态只做两件事：`ArchivedSessionGate`（`dsh-api-session-controller/lib/types/archived-session-gate.js`，
     只在 `agent/pre-step` 上 `{kind:'reject'}`，即禁止继续跑）＋ 客户端的可见性标记。
2. 客户端的行存在 `manager.summaries` 里，**归档只是把它藏起来**。删除时旧代码只做
   「把 id 从 `archivedSessionIds` 里摘掉」——遮罩一撤，**那行立刻重新可见**。
   外观上就等价于「已删除的归档会话又回来了」。
3. 旧代码唯一的客户端通知，是 `evictSessionFromMemory()` 里 `entry.detach()` **顺带**触发的
   `session/disposed → api-session/removed`。而这条链**只在会话仍驻留内存（live）时存在**；
   已归档、未打开的会话通常**不是 live** ⇒ **一个事件都不发**，行一直残留到重启。

## 完整事件链（每一跳都读源码确认）

```

  → dsh-api-remotes/lib/types/remote-events.js:18

```

对照 DSH 自己的写法（`dsh-api-session-controller/lib/index.js:2873-2878`）——它就是靠这个模式：

```js
ctx.on("session/created", (session) => ctx.emit("api-session/added", this.listState.summaryFor(session)));
ctx.on("session/disposed", (session) => ctx.emit("api-session/removed", session.id));
```

## 可复用要点

### 1. 插件可以直接 `ctx.emit` 走客户端事件

`ctx.emit` 不需要写进 `inject`：events 是 cordis 的 context mixin
（`cordis/lib/index.js:745-753` `this.mixin("events", ["on","once","parallel","emit","serial","bail","waterfall"])`）。
`mixin` 的 accessor 会把目标 ctx 与 service 用 `withProps` 合起来（`:891`），所以
`ctx.emit` 派发到的是**该 ctx 所在的那条 hook 链**，能命中共用同一 `_hooks` 表的其他插件
（`EventsService` 的 `_hooks` 是单例，`:377` `const hooks = this._hooks[name] ||= []`）。
本插件的 emit 被宿主上另一个探针插件当场记录到，即为实证。

### 2. 🔴 cordis 的 `emit` 是**同步且不隔离**的，必须自己包 try/catch

```js
// cordis/lib/index.js:280-282
emit(...args) {
  this.dispatch("emit", args).map((cb) => cb(...args));   // 任一听众抛错 ⇒ 直接冒泡给发射方
}
```

对比 cordis 自己的 `emitPluginDisposed`（`:968-984`）——它的文档注释就是
*"Notify plugin teardown without allowing one observer to break ownership cleanup"*，
即**官方自己在包 try/catch**。

所以：**凡是「删除/清理已完成」之后发的通知，一律包 try/catch**，把异常降级为 `warnings[]`，
绝不能让第三方监听器的 bug 把已完成的删除变成「报错」进而误导用户以为没删掉。

### 3. 归档 ≠ 不记账：删除必须自己释放 `workspaceRegistry` 的 `sessionIds`

`dsh-workspace/lib/index.js:500-501` 写得非常明确：

> Archiving never touches workspace accounting — an archived session keeps its `sessionIds` slot
> so unarchiving restores its position.

也就是说**归档故意保留记账**，而 DSH **没有**提供任何「删除 + 解绑」的复合接口
（`dsh-api-workspace-controller/lib/typert.host.js` 只暴露
`archiveSession` / `unarchiveSession` / …，没有 delete composite）。
于是删除路径若不管记账，注册表会**永久**记账一个盘上已无、header 也读不回来的 id；
`bootstrap:762` 对 `sessionPaths` 缺失的 id 直接 `continue`，所以这条记录**只能手改
`workspace.json`** 才能清掉——实测确认：

| | 旧代码 | 新代码 |
|---|---|---|
| `workspace.json` 是否仍记账已删 id | **是**（残留） | **否** |

正确写法是走 `registry.list()` → `entity.detachSession(id)`，不要自己改 `sessionIds` 数组：

- `WorkspaceEntity.detachSession`（`dsh-workspace/lib/types/entity.js:109-113`）是**竞态安全**的
  官方写路径：成员判定发生在**域写链内**（`mutate` → `table.update`）；
- 无变化时它用内部哨兵 `unchangedSentinel` 中止该 slot ⇒ **不写盘、不发变更**；
- 它还会按 canonical-cwd 头索引**重滤** `sessionIds`（`:141`），而这正是 `validateStoredState`
  要求的约束（`:831-855` 会抛 `session '<id>' is accounted by both workspace '<a>' and workspace '<b>'`）。

⚠️ 注意 `entity.sessionIds` 这个 **getter 已按头索引过滤**（`:51-53`）：header 读不回来的 id
在 getter 里**看不见**，但**仍躺在** durable record 里。所以判定时要同时看原始
`entity.record.sessionIds`，否则会漏掉「正是要清的那种泄漏」。

### 4. `location.found === false` 是个必须处理的返回值

`resolveSessionLocation` 在**没有任何候选根命中**时，返回的仍是一个**拼出来的猜测路径**，
只有 `found: false` 标记它不存在（其文档注释已写明 "deletion then prunes the archive id only"）。
旧代码只判断 `path` 非空，于是拿这个假路径去 `rm -rf` ⇒ **必然失败** ⇒ 报「删除失败」，
且该 id **永远卡在归档集合里**。凡是用到这个函数的地方都要判 `found`。

### 5. 客户端的 `ctx` 不在组件作用域里（最容易写成死代码的坑）

`window.__ModuleLoader__.load({ id, factory })` 的 `factory(require)` **只注入 `require`**，
`ctx` 只存在于 `apply(ctx)` 里。组件若直接引用 `ctx.*`，那是**自由变量** ⇒ `ReferenceError`；
如果再被 `try/catch` 吞掉、promise 又直接丢掉，就得到**完全静默的死代码**。

本插件就中过：`ArchivedSessionsPage()` 原本**不接收任何参数**，函数体里的
`ctx.workspaces.refresh()` / `ctx.sessions.refresh()` / `ctx.timer.timeout` 全是自由变量
⇒ **刷新从未执行过**（连带 5 秒自动取消确认也是死的）。

正确做法（与 DSH 官方客户端插件一致）：由 `apply()` 把 ctx 通过 **slot props** 传进组件
——官方 `dsh-client-ui-settings-plugins/lib/client.js` 就是把 `t`/`renderSlot`/`useTabs`
按 props 注入组件的；slot 本身也会把 props 展开（`dsh-client-ui-renderer/lib/client.js:771-777`
`jsx(Comp, {...kit, ...injected, ...slotInjected.props, ...ownerProps})`）。

另外两点：
- `ctx.workspaces.refresh()` **不存在**，别写（客户端 workspace 服务没有 `refresh`）。
- `ctx.sessions.refresh()` **存在**（`dsh-api-session-controller/lib/client.js:3258-3260`
  → `manager.refreshList()`），且**必须 `await`** 才有意义。
- `ctx.timer` **存在**（`dsh-cordis-client-runner/lib/client.js` 的 `ClientTimerService`
  经 `ctx.mixin` 暴露 `timeout`/`interval`/`throttle`/`debounce`）。

### 6. 补拉会和删除事件「打架」吗？不会

`refreshList()`（`dsh-api-session-controller/lib/client.js:2603-2652`）有三重保护，
所以「await 一次全量 refresh」可以安全地当作兜底：

1. `mergeOrderedBaseline` 会**丢弃 baseline 中不存在的 id**
   （`lib/types/client/ordered-baseline.js` 文档原文："identities absent from the baseline are removed"）；
2. 拉取**期间**记录的 mutation 会在基线到达后**重放**（`:2617-2620` `removedSincePull`）；
3. 单飞（`listInflight`）复用进行中的拉取。

已用真实 `mergeOrderedBaseline` 跑仿真确认：remove 事件、await refresh 两条腿都能删掉该行，
且**拉取期间到达的 remove 不会被基线复活**。

### 7. `dsh.client.inject` 不是 cordis 注入，别塞不存在的包名

本插件曾声明 `"@deepseek-ai/dsh-client-runtime"`，而**该包在 DSH 里根本不存在**
（289 个 `@deepseek-ai/*` 包里没有这个目录，只有 `dsh-invariants/README.md` 正文提过这名字）。
按官方 `references/practices.md`，`dsh.client.inject` 条目**只用于激活顺序/预取**
（"entries only order activation and stay allowed"），不参与 cordis 注入；
真正决定模块图顺序的是 `dsh.client.external`（`dsh-client-modules/lib/index.js:415-437`
`orderByModuleGraph` 只遍历 `entry.external`，无法解析的名字**静默跳过**）。
留着一个解析不到的包名只会误导，已删除。

## 验证方式（可复现）

用独立 `DSH_HOME` 起 scratch 宿主（**不要**用 `dsh web`——那会启动名为 `web` 的 profile）：

```powershell
$env:DSH_HOME = 'C:\Users\xj\AppData\Local\Temp\scratchdsh'
dsh scratchweb --no-open --port 19400
```

关键：**必须用「非 live 的归档会话」复现**——live 会话会走
`entry.detach()` 的既有事件链，把 bug 遮住（这正是之前容易误判「Host 端没问题」的原因）。

A/B 对照（同一份输入：磁盘有目录 + 在归档集合 + 非 live）：

| | 旧代码 | 新代码 |
|---|---|---|
| 发给客户端的 `api-session/removed` | **0**（行残留＝本 bug） | **1** |
| 磁盘目录 | 已删 | 已删 |
| 归档集合 | 已清 | 已清 |
| 工作区记账（落盘 `workspace.json` 复核） | **仍记账** | **已释放** |
