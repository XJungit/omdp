# 决策：OpenCode Zen 走 9router，不自研 DSH provider 插件

## 背景

OpenCode Zen 免费层有客户端指纹门禁（四条判据），DSH 直接调用会被 403。
曾调研过三条路线：

| 路线 | 结论 |
|---|---|
| Fork 社区插件 `FishBottle7/opencode2dsh` | 放弃：其 master 的 session 非规范（`ses_`+24hex）、工具集原样透传；两个 PR 都没碰工具轴 |
| 自研 `@omdp/*` DSH provider 插件 | **放弃（本决策）** |
| 直接用 9router 网关 | **采用** |

## 决策与依据

**用 9router，不自研 provider 插件。** 三个理由，按权重排序：

1. **上游已经做完，且做得比我们计划的更完备。**
   9router ≥ v0.5.86 自己实现了：官方 `descending()` 时间算法生成规范 session、
   注入必需工具集（`["bash","glob","grep","read"]`）、按通道给对工具形状、
   强制 `stream:true`。尤其是**工具名注入后在响应侧再映射回原名** ——
   这解决了我之前分析出的「注入空壳工具被模型选中怎么办」问题，
   而我的方案只能靠「空壳工具实测 0/4 不被选中」这种概率性依据。自研 = 重写一遍且更差。

2. **门禁是移动靶，自研插件等于永久维护债。**
   该门禁已两次加严（第一波 UA+session；第二波工具对+流式），
   且第二次加严只用了 1 天就被我们观测到。自研插件意味着每次 Zen 变更都要自己跟；
   而 9router 是被大量用户使用的网关，**盯它的人比盯我们的多，修复也更快**
   （这次就是证据：我们刚做完热补丁，上游已经修好了）。

3. **我们的产出价值不在重实现，而在判据沉淀与验证能力。**
   这次真正有价值的产物是四维判据矩阵、三层验证脚本、以及
   「用对照组区分上游修复 vs 门禁放宽」的方法论 —— 这些在 9router 路线下**依然全部有效**，
   换成自研插件反而会被绑定到自己的实现细节上。

## 什么条件下重新考虑

- 9router 停止维护，或长期不跟门禁（判定方法：跑 A 层直连发现红灯，而 9router 新版仍红灯）；
- 需要接入 9router 不支持的端点/模型通道；
- 需要把指纹逻辑塞进 DSH 内部（例如网关不可用的离线场景）。

若届时重开，自查清单已备好：`tools/9router-fix/README.md` 的
「给『将来若还要自研 provider』的参考清单」；DSH 侧适配要点见
[`../../2026-09-18/dsh-internals/windows-shell-tool-pwsh-not-bash.md`](../../2026-09-18/dsh-internals/windows-shell-tool-pwsh-not-bash.md)。

## 可复用要点

- **"自己实现一遍"要先问上游跟不跟得上**：当一个依赖的问题正在被大量用户承受时，
  上游修复速度通常快于自研；先做能力沉淀，别急着写代码。
- **补丁退役 ≠ 工作白做**：判据与验证脚本从「修什么」转为「升级后回归测什么」，
  价值不降反升（因为门禁随时可能再变）。
- **决策要写清"什么条件下重开"**，否则将来只会重新讨论一遍同样的选项。
