# DSH 0.2.0-rc.1：API 面零变化，却被门禁全部跳过

**日期**：2026-09-28
**分类**：dsh-compat
**涉及插件**：`@omdp/dsh-connector` 0.3.6 → 0.3.7、`@omdp/dsh-key-fallback` 3.2.3 → 3.2.4、
`@omdp/dsh-archived-sessions` 0.3.7 → 0.3.8（`@omdp/dsh-vision-bridge` 0.1.12 无 dsh peer，无动作）

## 背景 / 问题

DSH 桌面端升级到 `0.2.0-rc.1` 后，用户报告「插件异常」。实测现象：

| 探测 | 结果 |
|---|---|
| `GET /connector/api/mcp` | **404** |
| `GET /dsh-key-fallback/pools` | **404** |
| `POST /dsh-archived/list` | **405**（前缀路由未注册） |
| `GET /vision-bridge/capabilities` | **200** ✅ |

设置页里 connector / key-fallback / archived-sessions **三项整项消失**，而 vision-bridge 活着。

## 根因

**不是崩溃，是版本门禁第二次生效**：

三个插件声明的 `@deepseek-ai/dsh` peer 枚举止于 `0.1.7-rc.2`，运行版本已变成 `0.2.0-rc.1`：

```js
semver.satisfies('0.2.0-rc.1', '0.1.7-rc.1 || 0.1.7-rc.2', { includePrerelease: true })  // false
```

npm semver 对含预发布的 range **只匹配同一 `[major,minor,patch]` 三元组内的预发布**，
跨 `minor`（0.1 → 0.2）必然不满足 ⇒ `evaluatePluginCompatibility()` 返回不满足 ⇒
`skipping profile bundle` ⇒ 插件根本没被加载。

**vision-bridge 是天然对照组**：它没有声明任何 `@deepseek-ai/dsh*` peer，
而门禁**完全跳过没有 peer 的 manifest**（源码 `dsh-app-boot/lib/index.js` 里 `evaluatePluginCompatibility`
对 `peerDependencies` 为空的清单直接返回 `undefined`），所以它是唯一不受影响的。

> 结论：**「插件整项消失 + 路由 404/405、但 DSH 本体正常启动」= 门禁跳过，不是代码 bug。**
> 先跑门禁函数、再看 `skipping profile bundle` 日志，最后才查源码。

## 核查过程与结论（可复用方法）

### 1. 官方 tarball 全量逐文件 diff（首要证据）

下载 `0.1.7-rc.2` 与 `0.2.0-rc.1` 两版 `@deepseek-ai/<pkg>` 官方 tarball，解包后对 `lib/`
下**每个文件算 SHA1** 比对：

| 包 | `lib/` 变化 | 影响 |
|---|---|---|
| `dsh-credentials` / `dsh-llm` / `dsh-settings` / `dsh-shell` / `dsh-tools` | **0 文件变化** | 三个插件的调用面零变化 |
| `dsh-mcp-client` / `dsh-web` / `dsh-agent` / `dsh-agent-preset` | **0 文件变化** | 同上 |
| `dsh-session` | 5 文件变化 | **纯附加**：新增导出 `ToolCallRecovery` / `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN`，既有导出（`SessionStore` 等）零删除 |
| `dsh-tool-cordis` | `types/api-catalog.js` | 目录数据，与插件无关 |
| `dsh-app-boot` | `lib/index.js` | 门禁本体 |

**方法要点**：导出集合比对要同时检查「新增」与「删除」——只统计删除数会漏掉「新增也可能破坏」
的情形（本次是纯新增，安全），而只看文件哈希又会把「纯附加」误判成破坏。
「哈希 + 导出集合」两者合起来才能定性。

另做**方法级存在性复核**（在解包后的实现文本里正则检索方法名）：`credentials.resolve/describe/
set/unset`、`llm.listProviders/listModels/resolveModelInfo/stream`、`settings.replace/set`、
`tools.guard/register`、`shell.execute/resolve/result` —— 两版**全部命中、零缺失**。
（这一步是为了防止「文件没变但导出被 re-export 屏蔽」这类假阴性。）

### 2. 用新版门禁函数判新旧两种声明

沙箱安装官方 `@deepseek-ai/dsh@0.2.0-rc.1`（542 个包，npm 安装约 9 分钟），
直接 `import` 其 `dsh-app-boot`，调用真实的 `evaluatePluginCompatibility(manifest, {}, runtimeVersion)`：

```
❌ 拦截  @omdp/dsh-connector@0.3.6         → 不满足: dsh@0.1.7-rc.1 || 0.1.7-rc.2
✅ 放行  @omdp/dsh-connector@0.3.7
❌ 拦截  @omdp/dsh-key-fallback@3.2.3      → 不满足: dsh / dsh-llm / dsh-settings / dsh-credentials
✅ 放行  @omdp/dsh-key-fallback@3.2.4
❌ 拦截  @omdp/dsh-archived-sessions@0.3.7 → 不满足: dsh
✅ 放行  @omdp/dsh-archived-sessions@0.3.8
✅ 放行  @omdp/dsh-vision-bridge@0.1.12    （无 dsh peer，门禁不适用）
```

### 3. 真机装配（比「只看声明」强得多）

沙箱里准备独立 `DSH_HOME` + 一个 `smoke` profile（bundles 指向四个插件），
用**官方运行时**执行：

```powershell
$env:DSH_HOME = "$env:TEMP\shim020\home"
node "$stage\node_modules\@deepseek-ai\dsh\lib\bin.js" --profile smoke --dump-config
```

判据三条：① 四个插件都出现在 `--dump-config` 的装配树里；② 输出里没有
`incompatible` / `skipping profile bundle` / `ERR_`；③ `dsh --version` 确认是目标版本。

**`--dump-config` 是性价比最高的真机验证**：不启 web、不需要浏览器、不碰用户真实 profile，
一条命令就能确认「某个 bundle 到底进没进树」。

### 4. 发布件复核

`npm pack` 打**真实 tarball**（不是读仓库文件），再从 tarball 里 `tar -xzOf ... package/package.json`
读出清单，确认新枚举已进包，并让门禁函数对 tarball 内的 manifest 再判一次。

## 可复用要点

1. **门禁只拦「声明过 `@deepseek-ai/dsh*` peer 的插件」**。没声明的（如 vision-bridge）
   在任何 DSH 版本上都不会被跳过——代价是**没有自动保护**，兼容性只能靠运行时行为证明。
   本次事故里它恰好成了根因的对照实验。
2. **诊断口诀**：DSH 本体正常启动 + 某插件整项消失 + 该插件路由 404/405 ⇒ 先怀疑门禁。
3. **预发布版本必须逐版本追加枚举**：跨 `minor` 的升级（`0.1.7-rc.2 → 0.2.0-rc.1`）下，
   任何 `^0.1.7-rc.2` / `<0.2.0` 式范围都不可能放行，只有显式列出新版本。
   （这也是仓库规范 3「只枚举实测版本」的必然代价与价值：升级后插件会**优雅跳过一次**，
   提醒你去核查，而不是带着未验证的假设继续跑。）
4. **升级 DSH 后要同时核查两件独立的事**：① 官方包 API 有没有破坏性变化；
   ② 门禁声明有没有跟上。本次 API 面**逐字节零变化**（本可零改动兼容），
   却因为声明没跟上而全部被跳过——**两关都过才算适配完成**。
5. **0.2.0 的运行时不再来自全局 npm**：桌面端把 runtime 打进 `app.asar`
   （`@deepseek-ai/dsh-desktop-runtime@0.2.0-rc.1`），旧的
   `~/.dsh/profiles/node_modules/@deepseek-ai/*` junction 会变成悬空链接
   （`readFileSync` 报 ENOENT 是正常现象，不是环境坏了）。要在沙箱验证就单独
   `npm install @deepseek-ai/dsh@<ver>` 到临时目录，用它的 `lib/bin.js`。
6. **冒烟沙箱三件套**：独立目录装官方 runtime → 独立 `DSH_HOME`（`$env:DSH_HOME`
   指过去）→ profile 里 `dependencies` 用 `file:` 指向本地改过声明的插件。
   全程不碰用户真实 profile，也不需要 pnpm 在真实 profile 里跑 `install`。
