# 第三方插件在 0.2.0-rc.1 下"全灭"：门禁只读字面量 peer，pnpm patch 是唯一持久解

## 背景 / 现象

DSH 升级到 `0.2.0-rc.1` 后，用户报告：**除了「预设」（dsh-preset-craft-bot）和「视觉插件」
（@omdp/dsh-vision-bridge）不显示异常，其余插件全部异常**（设置页条目消失、
HTTP 路由 404/405）。

第一直觉是"插件代码不兼容"，实际不是。用真门禁逐个 bundle 跑，得到精确分组：

| bundle | dsh* peer 条数 | 门禁结果 |
|---|---|---|
| `@omdp/dsh-vision-bridge@0.1.12` | **0** | ✅ 放行 |
| `dsh-preset-craft-bot@0.2.0` | **0** | ✅ 放行 |
| 其余 9 个 | 1–16 | ❌ 全部拦截 |

## 根因

门禁函数 `evaluatePluginCompatibility()`（`dsh-app-boot/lib/index.js`）第一行就是：

```js
if (!Object.hasOwn(fields, "peerDependencies")) return void 0;   // 直接放行
```

**没声明任何 `peerDependencies` 的插件，门禁根本不看它** —— 这两个之所以"正常"，
不是因为他们兼容，而是因为**门禁管不着**。反过来，只要插件声明了
`@deepseek-ai/dsh*` peer，运行时一换版本、声明范围对不上，就会被整包拦下。

判定逻辑（同函数）：

```js
const issue = requirement.trim() === "" ||
  !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })
```

关键 semver 规则：**含预发布的 range 只在同 `[major,minor,patch]` 三元组内匹配预发布**，
所以 `^0.1.7-rc.2` / `>=0.1.7-rc.1 <0.1.8` 永远不可能满足 `0.2.0-rc.1`，
跨 `0.1 → 0.2` 必须显式枚举。

## 真正的坑：为什么"手改 node_modules 的 package.json"没用

第一反应是直接改 `node_modules/<pkg>/package.json` 里的 peer 范围。**这是错的，有三层原因**：

1. **硬链接污染共享 store**：`pnpm` 用内容寻址存储，`node_modules` 里的文件是**硬链接**
   （`Get-Item` 的 `LinkType = 'HardLink'`，`fsutil hardlink list` 能看到 store 里的孪生路径）。
   就地改写会同时改掉 store 中的那份，污染其他项目的共享文件。
2. **`pnpm install` 会还原**：DSH 在启动/更新流程里会跑 pnpm，被改的文件会按 lockfile 恢复。
3. **`packageExtensions` 也不管用**：实测它**只把扩展写进 lockfile**
   （`packageExtensionsChecksum`），**不改磁盘上的 `package.json`**。门禁读的是磁盘
   `packageDir/package.json`，所以读不到。

## 结论：用 `pnpm patch`（唯一同时满足"持久 + 可审计"的方案）

```
pnpm patch <pkg>@<ver>           # 复制包到 .pnpm_patches/ 并可编辑
# 编辑其中的 package.json，追加范围
pnpm patch-commit <该目录>        # 生成 patches/*.patch 并登记 patchedDependencies
```

实测优点：

- ✅ 在 `pnpm-workspace.yaml` 里生成可评审的 `patchedDependencies` 清单 + `patches/*.patch` 文本；
- ✅ **跨 `pnpm install` 存活**（连续 2 次 install 后仍在）；
- ✅ **跨 `--frozen-lockfile` 存活**；
- ✅ 安装后文件不再是 store 硬链接，`LinkType` 为空 —— 不污染共享 store。

### 关键细节：key 要用 range，不能用精确版本

`patchedDependencies` 的 key **必须能匹配到实际解析出的版本**，否则 pnpm **直接报错中止安装**：

```
Either remove them from "patchedDependencies" or update them to match packages in your dependencies.
```

实测 `dsh-cost-meter` 的真实教训：`^1.7.41` 在无 lockfile 的新解析下会装到 `1.7.43`，
此时 `dsh-cost-meter@1.7.41` 这个精确 key **匹配不上任何包 → 安装失败**。
改成 range key（`dsh-cost-meter@^1.7.41`）后：

- 补丁仍然生效（甚至能作用于 1.7.43 —— 补丁是按行匹配的 diff，peer 那几行没变，所以能应用）；
- 全新解析（无 lockfile）下也成功。

**所以 key 应与 `dependencies` 的 specifier 保持一致**（`^1.66.3` → `dshmarket@^1.66.3`），
`github:` 这类则用解析后的版本号。

## 另一个坑：`desktop` profile 不能离线自检

```
dsh --profile desktop --dump-config
→ error: profile "desktop" is managed exclusively by the Electron application
```

`desktop` 是 Electron 保留 profile，**不能用 CLI 装配自检**。所以验证要**把清单 + 补丁
复制到隔离 `DSH_HOME` 下的副本 profile** 做（只复制 `package.json` /
`pnpm-workspace.yaml` / `.npmrc` / `patches/`，不复制 `node_modules`），
在副本里 `pnpm install` → `dsh --profile <副本> --dump-config`。

本次副本实测（全新解析、补丁 key 用 range）：

- pnpm install 退出码 0；
- 6 个补丁包全部改写到位（`dsh-cost-meter` 自动涨到 1.7.43 后补丁仍生效）；
- `dump-config`：`incompatible` 0 处、`skipping profile bundle` 0 处、`ERR_` 0 处；
- 11 个插件全部进入装配树。

## 可复用要点

- **诊断启发式**：DSH 能启动 + 某个插件的设置项消失 + 它的路由 404/405 ⇒ 先怀疑门禁，别先怀疑代码。
- **"哪些插件没被拦"要看它有没有声明 peer**，不是看它是否真兼容。
- 改第三方插件声明，用 `pnpm patch`，别手改 `node_modules`；`packageExtensions` 对门禁无效。
- `patchedDependencies` 的 key 用 range，跟 `dependencies` 的 specifier 对齐。
- 自检用隔离 `DSH_HOME` 的副本 profile；`desktop` 是保留名，CLI 不能用。
- 上游插件发新版修好声明后，应删掉对应补丁回到真实声明。
