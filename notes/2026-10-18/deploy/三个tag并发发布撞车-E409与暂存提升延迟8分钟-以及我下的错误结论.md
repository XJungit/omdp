# 三个 tag 并发发布撞车：E409、暂存提升延迟 8 分钟，以及我先下的错误结论

日期：2026-10-18
涉及：`.github/workflows/publish.yml`、`docs/npm-publish.md`、`dsh-connector/package.json`
最终结果：`@omdp/dsh-connector` 的 **`0.3.9` 与 `0.3.10` 都已发行**（`latest = 0.3.10`，
两者代码逐字节相同）；`@omdp/dsh-key-fallback@3.3.3`、`@omdp/dsh-archived-sessions@0.3.11` 正常发行。

> ⚠️ 本篇同时记录**一次我自己的误判**。先给结论：**竞态是真的，修复是对的，
> 但我当时「版本号被永久卡死」的判断是错的** —— 暂存条目在 8 分钟后自行提升发布了。

## 事故

三个 tag 在几秒内先后推送：

```sh
git tag v0.3.9-dsh-connector v3.3.3-key-fallback v0.3.11-archived-sessions
git push origin v0.3.9-dsh-connector
git push origin v3.3.3-key-fallback
git push origin v0.3.11-archived-sessions
```

`on: push: tags` 是**每个 tag 起一个 run**，于是 3 个 run 并发；而旧 workflow 每个 run 都
**遍历全部包**去 publish ⇒ 三个 run 争抢同一批版本。

npm 是**暂存发布**：`npm publish` 一开始上传，版本号就被占用，抢输的一方拿到

```
npm error 409 Conflict - PUT https://registry.npmjs.org/@omdp%2fdsh-connector
npm error Cannot publish over previously staged version "0.3.9".
```

## 我的错误结论（本篇最该记住的部分）

我在 ≈10:35 观察到 **`npm view` / registry 都 404**、packument `modified` 没动、
重跑仍然 `409`，于是断定「暂存条目从未被提升 ⇒ 这个版本号永久卡死 ⇒ 必须顺延」，
并把该结论写进了 6 处文档。**8 分钟后 `0.3.9` 自己出现了。**

错误模式：**把「暂时观察不到」当成了「永久不会发生」。**

- 负面结论（「永远不会」「已经永久损坏」）需要**跨足够长时间跨度的重复观察**，
  而我只在 10:32–10:35 这个窗口里抽了两次样，恰好都落在提升延迟之内。
- 对比 2026-09-24 的同型事故：那次暂存条目也是「几分钟后自己出现」。
  **两次的先例都指向「等一等就好了」，我却在第二次反而下了更绝对的判断。**
- 正确写法应是**带时间戳的观察**：「截至 10:35（上传后约 6 分钟）仍为 404」，
  而不是「从未被提升 / 永久卡死」。

后果评估：**实际无害** —— `0.3.10` 与 `0.3.9` 的 tarball 逐文件比对后，除 `README.md`
与 `package.json` 外全部逐字节相同（`index.js` / `client.js` / `cordis.patch.yml` / `LICENSE`），
`latest` 指向 `0.3.10`，两个版本都能正常工作。代价是白烧了一个版本号，以及
**先把错误结论写进了文档，事后必须回头改**。

> 可复用判据：**npm 暂存提升的延迟可能达到 8 分钟以上。**
> `E409 Cannot publish over previously staged version` 的真实含义是
> 「有人正在处理这个版本号，别挤」，**不是**「它坏了」。
> 补救顺序应当是 **先等（≥15 分钟、间隔多次复查）→ 仍然不行才顺延版本号**。

## 根因（这部分结论仍成立）

### 根因 1：并发重叠（与 2026-09-24 事故同型）

旧 workflow 每个 run 都遍历全部包，N 个并发 run 必然争抢同一批版本。
即使不算「卡死」，也已经实打实地烧掉了两个红色 run 和一个版本号。

### 根因 2：「先探测 `npm view` 再发」挡不住这个竞态

2026-09-24 引入的 `if npm view "$name@$ver" ... then skip` 意图是「已发布就跳过」。
但**同批并发时对方此刻也还没发布**，探测必然回答「没发过」⇒ 三个 run 全都认为该发。

> 消除竞态只能靠消除**重叠**（让并发方各自处理不相交的资源），
> 不能靠「先查一下再动手」。查-改之间的窗口正是竞态本身。

### 与 2026-09-24 的关系

`notes/2026-09-24/deploy/concurrent-tags-and-masked-publish-failures.md` 已完整记录同一根因，
且当时就写下了「更稳的做法是让 workflow 只发布与该 tag 对应的那一个包……本仓库暂用
『遍历全部 + 已发布跳过』，故流程上限制一次一个 tag」。那一轮只落地了**流程约定**，
结构性修复被搁置 —— 于是本轮一旦违反约定（一次推 3 个 tag），故障立刻复现。

## 修复（与误判无关，仍然成立）

### workflow 只发布「本 tag 所指名的那一个包」

```yaml
- name: Publish packages
  run: |
    set -euo pipefail
    tag="${GITHUB_REF_NAME}"
    target=""
    for dir in dsh-connector dsh-key-fallback dsh-archived-sessions; do
      name=$(node -p "require('./$dir/package.json').name")
      ver=$(node -p "require('./$dir/package.json').version")
      short="${name#@omdp/}"   # @omdp/dsh-connector -> dsh-connector
      bare="${short#dsh-}"     # -> connector（历史 tag 两种写法都出现过）
      if [ "$tag" = "v$ver-$short" ] || [ "$tag" = "v$ver-$bare" ]; then
        target="$dir"
        echo "tag $tag -> $dir ($name@$ver)"
      fi
    done
    if [ -z "$target" ]; then
      echo "::error::tag '$tag' 未匹配任何活跃包的 <version>-<plugin>……"
      exit 1
    fi
    # …只对 $target 做「已发布则 skip，否则 publish」
```

三个要点：

1. **`dsh-` 前缀两种写法都接受** —— 历史 tag 里 `v0.3.8-dsh-connector` 带前缀，而
   `v3.3.1-key-fallback` / `v0.3.10-archived-sessions` 不带，命名并不统一。
2. **匹配不上就红**，不再回退成「遍历全部发」：这正是「忘了升 `version` 就打 tag」
   的信号，宁可让 CI 失败，也不要重演「顺手把别的包也发了」。
3. 保留「先探测 registry → 已发布则 skip」，它对付**重跑同一个 tag** 仍然正确（幂等），
   只是别指望它挡并发。

### 版本号顺延（事后看是多余的，但已发生）

`dsh-connector` 由 `0.3.9` 顺延为 `0.3.10`，内容一字未改。`0.3.9` 随后也自行发布了，
**两个版本并存**，`latest = 0.3.10`，用户装 `^0.3.9` 或 `^0.3.10` 都解析到 `0.3.10`。
不做撤回：撤回已发布版本会造成额外扰动，而两者代码等价。

## 可复用要点

1. 🔴 **负面结论需要更强的证据**（本篇最大教训）。「暂时观察不到」≠「永久不会发生」。
   写「永远不会 / 已永久损坏」之前，必须有跨足够长时间跨度的多次复查；
   否则只能写**带时间戳的观察**：「截至 HH:MM（上传后约 N 分钟）仍为 404」。
2. 🔴 **npm 暂存提升延迟可达 8 分钟以上**。`E409 … previously staged version` 的含义是
   「有人正在处理，别挤」，不是「坏了」。补救顺序：**先等（≥15 分钟）→ 再顺延版本号**。
3. ⚠️ **「先查再改」不是同步原语**。查-改窗口就是竞态窗口；能消除重叠就不要靠检查。
4. ⚠️ **`on: push: tags` 的 workflow 应按「一个 run 只处理一个 tag 对应资源」设计**。
   「遍历全部 + 已发布跳过」在有并发时必然争抢。
5. ⚠️ **流程约定是临时措施，不是修复**。2026-09-24 已识别出结构性方案却只落了约定，
   两个月后同一故障复现。识别出「更稳的做法」时，要么当场做，要么在文档里把它标成
   **未偿技术债**。
6. **绿色 workflow ≠ 制品已交付；红色 workflow 也 ≠ 制品没交付。**
   判据只有直连 registry API。本轮 run 39119406932 是 `success` 而它名下的 `0.3.9`
   当时确实还没落地；反过来两个红 run 也并没有毁掉任何东西。
7. **验证 workflow 改动不要只靠读**：YAML `parse()` + 把 run 块导出成真脚本用桩命令跑，
   能在一次 push 之前把命中 / skip / 不命中三条分支全部走一遍。
