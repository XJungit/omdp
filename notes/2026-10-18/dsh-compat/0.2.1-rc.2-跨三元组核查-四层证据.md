# DSH `0.2.1-rc.2` 跨三元组核查：四层证据与门禁函数的三处演进

**日期**：2026-10-18　**分类**：dsh-compat
**结论**：三个活跃插件（connector / key-fallback / archived-sessions）**源码零改动**即兼容
`0.2.1-rc.2`，只需在 peer 里新增第二段三元组区间。

## 背景

DSH 发布 `0.2.1-rc.2`（新三元组 `0.2.1`）。按 `AGENTS.md` 规范 3，跨三元组必须**先核查再放行**，
不得预先放宽。此前三个插件的 dsh peer 都是单段 `>=0.2.0-rc.1 <0.2.1-0`；用**真门禁函数**
实测，旧声明在 `0.2.1-rc.2` 上会被**整包跳过**（`skipping profile bundle`）。

## 核查方法（四层，逐步加强）

### 第 1 层：全量包级差异

`0.2.0-rc.2` → `0.2.1-rc.2`，覆盖全部 `@deepseek-ai/*` 包，逐文件 SHA256：

| 指标 | 数值 |
|---|---|
| 包数 | 288 → 305 |
| 有变化的包 | 273 |
| 其中有真实 `.js` 改动 | **177** |
| 仅版本号噪声 | 91 |
| 仅 `.d.ts` | 5 |
| 逐字节相同 | 4 |
| 从 CLI 依赖树消失 | 11 |
| 新增 | 28 |

⚠️ 「消失的 11 个」**在 npm 上仍有 `0.2.1-*` 版本**（属 client/web 侧，不进 CLI 依赖树）；
唯二例外是 `dsh-invariants` 与 `dsh-experimental-schedule-bundle`（无任何 `0.2.1-*`），
另 `dsh-subagent-in-process-driver` 只有 `0.2.1-alpha.1`。

### 第 2 层：消费面真实 ESM 导出集比对

不只 diff 文件，而是真的 `import()` 每个包、比对命名导出集合（**新增和移除都要看**）：

| 包 | 结论 |
|---|---|
| `dsh-credentials`(9) / `dsh-llm`(66) / `dsh-settings`(4) / `dsh-workspace`(12) / `dsh-session-query`(17) / `schemastery`(1) | **完全一致** |
| `dsh-session` | 28 → 30（纯新增 `appendPluginRecord` / `pluginRecordOf`） |
| `dsh-app-boot` | 移除 2 个（未使用），新增 7 个 |
| `dsh-session-persistence-jsonl` | **移除 `default`**（见下） |

### 第 3 层：调用符号存在性

12 个包 / **37 个我们实际调用的符号**逐个正则复核，**零缺失**。

### 第 4 层（决定性）：真实 CLI 装配

用真实 `0.2.1-rc.2` CLI + **隔离 `DSH_HOME`** + `link:` 指向仓库里的插件源码，跑
`node <pkg>/lib/bin.js --profile smoke --dump-config`：三个插件**全部进树**
（`- id: connector` / `key-fallback` / `archived-sessions`）、**零 skip / 零不兼容告警**、退出码 `0`。

## 两处需要解释的移除项

### 1. `dsh-session-persistence-jsonl` 的 `default` 消失

- A（`0.2.0-rc.2`）：`{JsonlCompressionSchema, default}`
- B（`0.2.1-rc.2`）：`{Config, JsonlCompressionSchema, apply, name}`

该包从「带 default 导出的后端类」**改成了标准 cordis 插件模块**。

`dsh-archived-sessions/lib/index.js:339` 的写法是
`const backend = typeof jsonlBackend.sessionDir === "function" ? jsonlBackend : null`，
而 **`sessionDir` / `projectDir` 在两版里都是类方法、从来不是命名导出**
⇒ 该分支在 `0.2.0-rc.2` 上**本来就没命中过**，一直走插件内置的编码兜底。

**两版行为完全一致，无回归。** 代码里的注释声称「后端路径助手被导出并使用」与实现不符
（历史遗留描述，本轮未改源码，仅在文档中记录）。

### 2. `dsh-app-boot` 的导出增删

移除 `HARNESS_SOURCE_SECTION` / `addHarnessSourceSection`（我们未使用）；
新增 `readBundlePatches` / `recomposeProfile` / `resolvePluginResource` / `ON_DEMAND_BUNDLES` /
`OFFICIAL_ON_DEMAND_CATALOG` / `ProfileRuntimeResolution` / `ResolutionRestartRequired`。

## 🔴 门禁函数本身的三处演进

`evaluatePluginCompatibility()` 在 0.2.1 里被重构，三处变化都确认对我们无影响：

| 变化 | 内容 | 影响 |
|---|---|---|
| 字段改名 | `peers` → **`requirements`**（改由新函数 `unmetRequirements(fields, runtimeVersion)` 计算） | **无**：`scripts/check-peer-gate.mjs` 只判 `gate(...) === undefined`，不读返回字段 |
| 新增 `engines.dsh` | 若声明 `engines.dsh`，该字段**独占决定**结果，完全跳过 `peerDependencies` | **无**：我们没声明 `engines`；但脚本的回退谓词已同步这个优先级以保持等价 |
| prerelease 判定 | 内联判断改成 `satisfies()` 包装 | **无**：仍是 `semver.satisfies(v, range, {includePrerelease:true})`，语义未变 |

**可复用教训**：校验脚本**不要读门禁返回对象的内部字段**。只判「有没有返回」
（`=== undefined`），才能在门禁函数重构时保持稳定。本次若读了 `.peers`，就会在 `0.2.1` 上静默失效。

## 下界为什么取 `0.2.1-rc.1` 而不是实测的 `rc.2`

额外做了一轮 `0.2.1-rc.1` → `rc.2` 差异：303 → 305 个包，只有 **11 个包有 `.js` 改动**，
其中落在我们消费面里的**只有 `dsh-cordis-client-runner/lib/client.js` 一个文件**，
`schemastery` 甚至逐字节相同；导出面完全一致 ⇒ 取 `rc.1` 作下界安全，符合规范 3 的
「实测三元组首个 rc 即可放行其后续 rc 与正式版」。

## 反事实证明（证明装配测试真的敏感）

把 `dsh-connector` 复制一份、peer 改回旧声明 `>=0.2.0-rc.1 <0.2.1-0`，
在**同一个** `0.2.1-rc.2` 运行时上重跑 `--dump-config`：

```
dsh: skipping profile bundle "@omdp/dsh-connector-old": Error: Plugin @omdp/dsh-connector@0.3.9
is incompatible with dsh 0.2.1-rc.2: requirements {"@deepseek-ai/dsh":">=0.2.0-rc.1 <0.2.1-0"}.
Running it may cause crashes or data loss. … Exact-version exemption: not active.
```

同一次运行里，用**新声明**的 `archived-sessions` 照常进树。
⇒ 装配测试**确实能抓到回归**，不是「跑了个寂寞」。

## 放行边界（真门禁函数实测，3 插件 × 19 版本 = 57/57 全对）

- ✅ **放行**：`0.2.0-rc.1` / `rc.2` / `rc.3` / `rc.9` / `0.2.0`；`0.2.1-rc.1` / `rc.2` / `rc.3` / `0.2.1`
- ⛔ **拦截**：`0.2.1-alpha.1` / `alpha.5`（早于下界）；`0.2.2-rc.1` / `0.2.2-0`；`0.3.0-rc.1`；
  `0.1.7-rc.1` / `rc.2` / `alpha.1`；`0.1.8-rc.1`；`0.1.6-alpha.1`

## 可复用要点

1. **跨三元组核查的最小充分集**：①全量包级 SHA256（定范围）→ ②消费面导出集比对（找 API 断裂）
   → ③调用符号存在性（防漏网）→ ④真实 CLI 装配（终局证据）。
2. **装配测试必须做反证**，否则无法区分「真通过」和「根本没生效」。
3. **`cordis` / `schemastery` 的追加要跟着 DSH 的钉版走**：`0.2.1-rc.2` 钉
   `cordis ~4.0.5` / `schemastery ~3.18.5`，故追加 `4.0.5` / `3.18.5`。
   经查证 `4.0.3` / `3.18.3` **从未被任何 DSH 版本钉过** ⇒ 不枚举是正确的，别乱加。
4. 注册表检查必须走 **registry API 直连**（`https://registry.npmjs.org/@deepseek-ai%2Fdsh`），
   `npm view` 会命中本地 packument 缓存给出陈旧结果。
5. 隔离 `DSH_HOME` 是安全复现的关键——**不要**在用户正在跑的 profile 上做装配实验。
