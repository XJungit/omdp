# DSH 0.2.0-rc.2：API 面仍零变化，门禁第三次生效——且上轮的 pnpm patch 会随版本失效

**DSH 版本**：`0.2.0-rc.1 → 0.2.0-rc.2`（npm `latest`/`next` 均为 `0.2.0-rc.2`）
**场景**：预更新桌面版到 `0.2.0-rc.2`，问「哪些插件不兼容」

## 背景 / 现象

上一轮（`0.1.7-rc.2 → 0.2.0-rc.1`）已经踩过一次门禁，并用 `pnpm patch` 给两个第三方插件
补了声明。本轮 `0.2.0-rc.1 → rc.2` 又踩一次，且**多了一个新变量**：上轮的补丁因为只写了
`0.2.0-rc.1` 这个精确版本，在 rc.2 下**自动失效**。

## 根因

### 1. 门禁只看 `peerDependencies` 的字面量，运行时版本一换就重新判定

`dsh-app-boot` 的 `evaluatePluginCompatibility()` 判据：

```js
!semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })
```

`0.2.0-rc.2` 不满足 `0.2.0-rc.1`（预发布必须逐个枚举或同三元组范围）。
关键点：**`0.2.0-rc.1` 与 `0.2.0-rc.2` 是同 `[major,minor,patch]` 三元组**，所以
`^0.2.0-rc.1` / `>=0.2.0-rc.1 <0.2.1` 这类**范围**写法在 rc.2 下**成立**（实测 true）——
只有**逐版本精确枚举**的声明才需要再追加一项。

### 2. pnpm patch 是"按行匹配的文本 diff"，补丁内容本身不随运行时演进

上轮补丁写的是：

```diff
-    "@deepseek-ai/dsh-llm": "^0.1.5-rc.3",
+    "@deepseek-ai/dsh-llm": "^0.1.5-rc.3 || 0.2.0-rc.1",
```

补丁**成功应用**了（pnpm install 无错），但补出来的声明只认 `0.2.0-rc.1`，
rc.2 下照样被拦。**补丁生效 ≠ 补丁仍有意义**——这是本轮最大的认知增量。

### 3. 门禁在"启动装配"时也生效，不只是安装时

两处调用点都会拒：

- **安装期**：`dsh-plugin-manager/lib/types/operations.js` →
  `if (preflight.length > 0) return rejected(preflight, 'nothing was installed')`
- **启动期**：`dsh-app-boot/lib/index.js` → `prepareProfileEntries()` →
  `row.disabled = true` + stderr `dsh: disabling profile plugin ...`（旧版措辞
  `skipping profile bundle`；rc.2 实测两种措辞都出现过）

所以**已经装好的插件在启动时也会被整包拒活**，表现为设置页条目消失、HTTP 路由 404/405。

## 核查过程（本轮实际做的）

### A. rc.1 ↔ rc.2 全量 tarball 逐文件 SHA256 diff（20 个包）

结论：**插件调用面零变化**。

| 包 | 变化文件 |
|---|---|
| `dsh-credentials` / `dsh-settings` / `dsh-shell` / `dsh-session` / `dsh-host-webserver` / `dsh-web-app` / `dsh-attachment` / `dsh-tools` / `dsh-mcp-client` / `dsh-agent` / `dsh-session-persistence-jsonl` / `dsh-workspace` / `dsh-session-query` / `dsh-client-ui-settings` / `dsh-client-ui-slots` / `dsh-app-boot` / `dsh-base` | **只有 `package.json`（版本号）** |
| `dsh-llm` | `lib/typert.host.js` + `package.json` |
| `dsh-agent-preset` | `package.json` + `skills/.../packages.md`（文档） |
| `dsh` 主包 | `bin.js` / `plugin-*.js` / 三个 `.d.ts` / README |

- `dsh-llm` 的唯一代码变化是 `typert.host.js` 里内嵌 `MessageSourceMap` 类型**新增**
  `'user-question-reply'` 一个字段——附加式，插件不用它；
- `dsh` 主包的变化全部是 **`desktop` profile 支持**：新增 `requireDesktopProfile()`、
  `manageDesktopProfile` 选项、`runProfilePnpm`。rc.1 的 README 说 CLI 对 `desktop`
  「rejects boot, config-dump, **and plugin-management** requests」，rc.2 改成
  「rejects boot and config-dump；**npm CLI 也拒绝 plugin-management，但桌面版自带命令可以管**」。
  → **插件安装入口变了：rc.2 起桌面 profile 要用应用内置的命令装插件，npm CLI 管不了。**

### B. 真门禁判定（用 rc.2 自带的 `evaluatePluginCompatibility()`）

`runtimeVersion = 0.2.0-rc.2`：

| 插件 | 当前声明 | 判定 |
|---|---|---|
| `@omdp/dsh-connector@0.3.7` | 不含 rc.2 | ❌ 拦截（`@deepseek-ai/dsh`） |
| `@omdp/dsh-archived-sessions@0.3.8` | 不含 rc.2 | ❌ 拦截（`@deepseek-ai/dsh`） |
| `@omdp/dsh-key-fallback@3.3.1` | 不含 rc.2 | ❌ 拦截（dsh/credentials/llm/settings **四条**） |
| `@omdp/dsh-vision-bridge@0.1.12` | **零 peer** | ✅ 放行（门禁根本不看它） |

追加 `|| 0.2.0-rc.2` 后 → 三个全部 ✅ 放行。

### C. 真机装配复现（官方 `dsh@0.2.0-rc.2` + 隔离 `DSH_HOME` + desktop profile 副本）

`--dump-config` 的 stderr 实测被拒活清单（6 个）：

```
skipping profile bundle "@omdp/dsh-connector"
skipping profile bundle "@omdp/dsh-key-fallback"
skipping profile bundle "@omdp/dsh-archived-sessions"
skipping profile bundle "dsh-client-auto-continue"
skipping profile bundle "dsh-watcher"
skipping profile bundle "@wxg-prc-cpg/browser-skill-dsh-plugin"
```

未被拒（4 个）：`dsh-cost-meter`（用 `>=0.2.0-rc.1 <0.3.0-0` 范围 → 天然过）、
`dshmarket`（用 `^0.2.0-rc.1` 范围 → 天然过）、`@omdp/dsh-vision-bridge`（零 peer）、
`dsh-preset-craft-bot`（零 peer）。

## 本轮的处理结果（2026-09-30）

三个本仓库插件**不再走"枚举追加"这条老路**，而是按用户指示把声明改为
**三元组区间**——这是第 3 轮故障后终于修正了根因（声明写法），而不只是补上这一版：

| 插件 | 新版本 | 新声明 |
|---|---|---|
| `@omdp/dsh-connector` | `0.3.8`（原 0.3.7） | `>=0.2.0-rc.1 <0.2.1-0` |
| `@omdp/dsh-archived-sessions` | `0.3.9`（原 0.3.8） | `>=0.2.0-rc.1 <0.2.1-0` |
| `@omdp/dsh-key-fallback` | `3.3.2`（原 3.3.1） | 四条 dsh peer 均为 `>=0.2.0-rc.1 <0.2.1-0` |

⚠️ **同时收窄了支持面**：按用户要求只声明 `0.2.0` 线，`0.1.7` 线不再声明。
需要在 0.1.7 上运行的用户应钉旧版（`0.3.7` / `3.3.1` / `0.3.8`）。
`@omdp/dsh-vision-bridge` 无 dsh peer ⇒ 不受门禁影响，无需改动。

推导与 `-0` 边界坑详见
`notes/2026-09-30/plugin-dev/peer-三元组区间取代逐版本枚举.md`。

## 可复用要点

1. **诊断顺序**：设置项消失 + 路由 404/405 ⇒ 先看 stderr 有没有
   `skipping profile bundle` / `disabling profile plugin`，**先怀疑门禁，别先怀疑代码**。
2. **rc.1→rc.2 这类同三元组预发布升级，范围声明是免疫的，逐版本枚举声明必须追加**。
   所以「谁的声明写成了范围」决定了他会不会跟着炸——这是本轮 6 个被拦、4 个幸存的唯一分界线。
   → **推论**：自己也应该改用范围声明，而不是每轮追加枚举（本轮据此改了三个插件）。
3. **pnpm patch 不是一劳永逸**：补丁内容里的版本号也要随运行时演进，
   否则会「补丁应用成功但没用」。升级 DSH 后必须**复查补丁内容**，不只是复查补丁是否还在。
   ⚠️ 2026-09-30 实测补强：补丁里写**精确版本**（`|| 0.2.0-rc.1`）时，寿命被绑死在那一个 rc 上——
   连它本来能治的「装后复检 / 启动加载」门禁也一起失守（rc.2 下 `satisfies` → false）。
   补丁里要写版本就写区间；卸载这类插件时还会撞上 `ERR_PNPM_UNUSED_PATCH`。
   详见 `notes/2026-09-30/debug/卸载插件失败-ERR_PNPM_UNUSED_PATCH与补丁共存亡.md`。
4. **优先等上游原生修复**：`dsh-cost-meter` / `dshmarket` / `dsh-watcher` 都是上游改用范围声明后
   天然免疫的样本；补丁应尽量作为临时手段，上游发新版后要删补丁 + 抬钉版。
5. **自检方法**：`desktop` 是 Electron 保留 profile，CLI 不能装配自检
   （rc.2 起 `plugin-management` 也被 npm CLI 拒绝）。做法是
   **复制 `package.json` / `pnpm-workspace.yaml` / `.npmrc` / `patches/` 到隔离 `DSH_HOME` 的副本 profile**，
   在副本里 `pnpm install` → `dsh --profile <副本> --dump-config`，看 stderr 的 skipping 行。
6. **`dsh-client-runtime` 这个包不存在**（本轮 pack 时发现），写依赖时别引用。
