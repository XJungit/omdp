# 补丁改不了安装门禁：两道门禁、升级顺序、以及一次误判

## 背景

DSH 升到 `0.2.0-rc.1` 后，用户报「几个第三方插件没法更新」。
既有做法是用 pnpm 的 `patchedDependencies` 往插件 `package.json` 的
`peerDependencies` 里追加 `|| 0.2.0-rc.1`，让已装的插件能过门禁。
已装的全部 PASS，但一按「更新」就被拒：`installation rejected ... nothing was installed`。

## 根因：两道门禁，读的不是同一份 manifest

同一套 `evaluatePluginCompatibility()` 在两个地方被调用，读的 manifest 来源不同：

| 门禁 | 位置 | 读什么 | 补丁能否影响 |
|---|---|---|---|
| **安装前预检** | `dsh-plugin-manager/lib/index.js:500-514`；`lib/types/operations.js:296-319` | `namedSpecManifest()` → `pnpm view <spec> name version peerDependencies --json`，即 **registry 上的原始 manifest** | ❌ **不能**（补丁是 pnpm 装完才落盘的） |
| **装后复检 / 启动加载** | `lib/types/operations.js:443-478`；`dsh-app-boot/lib/index.js:2063-2084` `preflight()` | `manifestOf()` → 已装路径 `node_modules/<pkg>/package.json` | ✅ 能 |

`namedSpecManifest` 是决定性的一段：

```js
if (parsed.kind === "path") { /* 读本地 package.json */ }
if (parsed.kind !== "registry") return void 0;   // git/tarball → 直接跳过预检
const viewed = await execa("pnpm", ["view", parsed.spec, "name","version","peerDependencies","--json"]);
```

所以：
- **补丁只治「已装能不能加载」，治不了「新版本能不能装」**。这是死循环的技术本质：
  不更新就一直被旧声明卡着，更新要先过旧声明的门禁。
- **`github:` / `file:` 依赖不走安装预检**（`kind !== "registry"` 直接 `void 0`），
  但仍会走装后复检。

### 装后复检只拦「本次动过的包」

`operations.js:452`：

```js
const untouched = beforeDependencies[name] === spec && installedBefore.get(name) === installed;
```

`untouched` 的包只打 warning，**不**触发回滚。但——**这条防线救不了你自己删掉的补丁**。

## 关键教训：升级顺序错了会把自己锁死（本次实际踩到）

我按「先删 `dsh-watcher@0.6.1` 补丁条目 → 再升 0.7.0」的顺序做，结果：

1. 删掉 `patchedDependencies` 条目后，**已装的 0.6.1 立刻退回未打补丁状态**
   （peer 变回 `>=0.1.7-rc.1 <0.1.8`）。
2. 此时装 `dshmarket@1.66.6`，装后复检扫到 watcher（它 `untouched` 判定依赖
   `installedBefore` **内容**相同——但我改了 workspace 配置使内容已变），
   直接 `installation rejected` 并回滚 `package.json` + `pnpm-lock.yaml`。
3. 结果：watcher 卡在 0.6.1 且**无补丁** → 既过不了装后复检，也过不了启动门禁，
   dshmarket 也被连带回滚。

**正确顺序：先把补丁目标升到「上游已原生声明」的版本，再删补丁条目。**
本次修正后：watcher 升到 0.7.0（main 已声明 `>=0.2.0-rc.1 <0.2.1`）→ 补丁自然失效 → 删条目安全。

## `ambiguous-install`：专治「已装依赖改写成同值」

`installBundle` 成功后靠「依赖变化量」反推装了谁（`index.js:1778-1782`）：

```js
const installed = Object.keys(after).filter((name) => before[name] !== after[name]);
if (installed.length === 0) installed.push(...Object.keys(after).filter((name) => spec === name || spec.startsWith(`${name}@`)));
if (installed.length !== 1 || target === void 0) throw new ManagementFailure("ambiguous-install");
```

- 给**已装**的依赖重装同版本 → 没有 delta → `ambiguous-install`，
  且会回滚 `package.json`/`pnpm-lock.yaml`（`node_modules` 不动）。
- 本次解法：把 `github:aa2246740/dsh-watcher` 写成
  `github:aa2246740/dsh-watcher#main`，spec 变了 → delta 出现 →
  `stage: enable, changed: true`，lockfile 正确改钉 `7dbba248(0.7.0)`，
  且陈旧的 `patch_hash=` 后缀自然消失。

**结论：想让 git 依赖真正刷新，spec 必须有可见变化（加 `#main` / `#<commit>`）。**

## 唯一能解开「安装预检」的手段

不是补丁，是**官方精确版本豁免**：`profiles/desktop/compatibility.json`

```json
{ "dsh-client-auto-continue@0.12.0": ["0.2.0-rc.1"] }
```

- 键必须是精确 `name@version`，值必须是精确 DSH 版本数组
  （`readProfileCompatibility` `dsh-app-boot/lib/index.js:383-397` 会校验并忽略不合规项）。
- 实测反例：键写成 `0.11.9`（版本不符）或值写成 `0.1.7-rc.1`（运行时不符）**都仍然 BLOCK**。
- 代价：官方原文 "Running it may cause crashes or data loss"，需用户明示接受；
  且豁免按精确版本授予，上游每发新版都要重新授权。

## 可复用要点

- 「能加载」≠「能安装」。排查「装不上」先分清是哪一道门禁。
- 判断某个上游版本能否装：**取 registry 原始 manifest 跑门禁**，别用已装（已打补丁）的。
  `npm view <pkg>@<ver> --json` 返回的是 packument 形状，要取 `versions[ver]`
  并规整成 `{name,version,peerDependencies}` 再喂给 `evaluatePluginCompatibility`。
- 改 `patchedDependencies` 前先问：**已装的旧版会不会因此退回未补丁状态而被门禁拦？**
- git 依赖要刷新：spec 必须变化（`#main`）。
- 动手前备份 `package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml`。
