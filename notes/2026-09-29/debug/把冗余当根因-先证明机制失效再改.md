# 「有一处冗余代码无效」≠「机制失效」：一次被证伪的根因判断

**日期**：2026-09-29
**类别**：debug
**涉及插件**：`@omdp/dsh-key-fallback`（3.2.4 → 3.3.0 → 3.3.1）
**DSH 版本**：桌面端 `0.2.0-rc.1`

## 背景 / 问题

排查 `dsh-key-fallback` 的 key 轮换时，发现 `GET /dsh-key-fallback/pools` 返回的两个字段互相矛盾：

```json
{ "currentRef": "key_fallback_sensenova_key1",   // 池认为在用 key1
  "activeRef":  "SENSENOVA_API_KEY",              // 而 env 反查得到另一把
  "envSource":  "file" }
```

顺藤摸根，确认了一条**真实**的源码事实链：

```
dsh-app-boot :3435          const inherited = { ...process.env }        ← 启动时冻结
dsh-launch-environment :30  createLaunchEnvironmentSnapshot(layers)     ← 拷进 Map
profile-boot :274           hostCtx.provide(DSH_LAUNCH_ENVIRONMENT_KEY, environment)
dsh-credentials-local :427  inherited() 只读上面那个快照
```

⇒ 结论 A：**插件里那 5 处 `process.env[pool.cfg.env] = key.value` 是死代码**（写在了 Node 的
进程环境上，凭证层看的是启动快照）。**结论 A 正确。**

## 错误的那一步

由此直接跳到 **结论 B：「所以换 key 从未生效，每个请求都在用启动时那把旧 key」**，
并据此把 3.2.4 → 3.3.0 描述成「终于修好了轮换」，写进了：

- commit message
- `dsh-key-fallback/README.md` 与 `README.zh-CN.md` 的 v3.3.0 段落
- 根 `README.md`（中英两段）
- `docs/plugin-compatibility.md`（§4 正文 + 3 处表格 + 第 1 节 + 第 5 节）
- 笔记 `notes/2026-09-29/dsh-internals/process-env-写不进凭据层-启动环境快照.md`

**结论 B 是错的。** 证伪只用了三条命令：

```bash
# ① 这个包装是什么时候引入的？——答案是 v3.0.0 重写，不是 3.3.0
git log -S 'credSvc.resolve =' -- dsh-key-fallback/lib/index.js
#   → 75ea76a feat(dsh-key-fallback): v3 rewrite ... bump 3.0.0
#   → 13bae1d （本次）

# ② 已发布的 3.2.4 里到底有没有？——有
npm pack @omdp/dsh-key-fallback@3.2.4 && tar -xzf … && grep -n 'credSvc.resolve =\|pool-hit' package/lib/index.js
#   → 298: credSvc.resolve = async (ref) => {
#   → 305: if (cur) { diag('resolve','pool-hit ' + refName + ' -> ' + cur.ref); … }

# ③ 实机轮换时间线——一直在换
#   GET /dsh-key-fallback/diag（200 条）→ 两把 key 各用 26 / 25 次，逐次交替
```

真相：3.2.4 里**包装与 env 写入同时存在**，真正把 key 交给 provider 的**一直是包装**
（`dsh-llm-pi-ai:2563` 每次 generate 都调它）。那 5 处 env 写入是**并存的冗余**，
删掉是对的，但它**不是机制**，删它**不影响鉴权**。

v3.3.0 真正的影响其实只有一条是**可见行为**修复：`/pools` 的 `activeRef` 原先用
`process.env` 值反查池成员、只在没匹配时回退 `currentRef`，所以**会高亮错误的那把**
（正是上面那个矛盾 JSON 的来源——它是**显示 bug**，不是交付 bug）。
其余是：删冗余写入、给 `agent/request-error` 的归因加守卫、`ctx.effect` 卸载还原。

## 为什么会误判

1. **只读了「可疑的那段代码」，没读「同文件里已经在工作的那段」。**
   排查时读的是 3.2.4 的 `process.env` 写入（显眼且确实可疑），
   却**没有同时读同一个文件里的 `credSvc.resolve = …`**。
   → 正确做法：`git show <rev>:<path>` 通读**改动前**的实现，而不是只搜自己怀疑的关键字。
2. **把「一处路径无效」升格为「功能无效」。**
   那 5 处写入只是**其中一条**路径；功能走的是另一条。
   → 要断言「功能失效」，必须**证明交付路径失效**，而不是证明某段旁路代码失效。
3. **矛盾的 UI 字段被当成了交付证据。**
   `activeRef` 是**自己实现的（有 bug 的）反查**，不是 provider 实际收到的 key。
   → 交付证据只有两类：`pool-hit` 这类**交付路径上的日志**，或**出站请求本身**
   （`Authorization` 头 / `x-api-key`）。

## 可复用要点

- **判定「功能是否失效」前，先定位它实际走的那条路径**：`git log -S` 追溯引入点、
  `git show <rev>:<path>` 读改动前的完整实现。**禁止**只看文档描述、只看自己怀疑的关键字、
  或只读 diff。
- **区分「旁路代码无效」与「主路径失效」**。二者结论差一个数量级：
  前者是清理，后者才是 bug 修复。表述上必须严格对应证据强度。
- **UI 字段 ≠ 交付证据**。界面上的「当前使用」是插件自己算出来的投影，可能有 bug。
  交付证据取在交付路径上（`pool-hit` 日志）或出站字节（`Authorization` 头）。
- **发布描述比 bug 更难收回**。错误结论一旦进了 npm tarball 里的 README，
  就只能靠**再发一版**更正（本次即 3.3.1 纯文档版）。
  ⇒ 涉及「原来是不是坏的」这类**历史事实断言**时，落笔前先跑一次证伪命令。
- **改动前的基线要留证**：`npm pack <pkg>@<发布版>` 下载 registry 上的实际产物核对，
  比翻 git 历史更直接（发布产物才是用户真正装到的东西）。
